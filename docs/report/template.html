제품 개요

1.1 제품 정의

Whenly 는 사용자가 스크린샷을 공유하면 그 안의 텍스트를 인식하고 문맥을 해석하여 제목과 마감이 있는 할 일로 변환하고, 마감 전에 알림을 제공하는 개인 비서 애플리케이션이다. iOS 와 macOS 를 대상으로 하며, 문맥 해석을 담당하는 분석 백엔드를 포함한다.

1.2 해결 대상 문제

사용자는 메신저·예약 화면·공지·SNS 에서 “나중에 해야 할 것”을 스크린샷으로 저장하지만, 해당 이미지는 사진첩에 축적될 뿐 실행으로 이어지지 않는다. 실행하려면 사용자가 (1) 이미지를 다시 찾아 읽고, (2) 날짜를 판별하고, (3) 할 일 앱과 캘린더에 중복 입력해야 한다.

대부분의 경우 이 세 단계는 수행되지 않는다. 스크린샷은 기록했다는 인식만 제공하고, 마감은 그대로 경과한다.

1.3 제품 약속

스크린샷을 한 번 공유하면 해야 할 일이 정리되고, 마감이 다가오면 알려 준다.

1.4 대상 사용자

예약·공지·업무 요청·행사 정보를 스크린샷으로 저장하는 빈도가 높은 iPhone 사용자. 대표적인 일과 — 병원 예약 확정 문자, 관리비 고지, 행사 안내, 회의 시간 변경. 전부 화면에 존재하고, 전부 후속 조치가 필요하며, 전부 사진첩에 축적된다.

8.2 macOS 플로우 차이

macOS 에서는 물방울에 드롭하면 명확한 경우 즉시 등록하고 “넣었어요 · 실행 취소 · 고치기” 배너를 8초간 표시한다. 모호한 경우 확인 창을 연다. 확인 단계를 제거한 것이 아니라 저장 전 확인과 저장 후 되돌리기로 분기한 것이며, 판정 기준은 AutoFilePolicy 단일 지점에 있다.

날짜 없음                  →  확인 요청 ("날짜를 찾지 못했어요")
ambiguities 비어 있지 않음  →  확인 요청 (해당 모호점을 그대로 표시)
confidence < 0.80           →  확인 요청
그 외                       →  즉시 등록 + 되돌리기 배너

ambiguities 를 confidence 보다 먼저 평가한다. 실제 호출에서 confidence 가 0.9~1.0 구간에만 분포하여 판별력을 갖지 못하기 때문이다 (§16).

macOS 앱의 플로팅 물방울과 메뉴바 항목에 대한 디자인 요구사항의 구현 가능성을 검증하고 대안을 제시한다. 추정이 아니라 실측에 근거한다 — 검증 실험 4건을 수행했으며 결과 이미지는 전부 실제 화면 캡처다.

A.1

요구사항 정의

#요구사항판정

A.2

메뉴바 아이콘

A.2.1 플랫폼 제약

메뉴바 아이콘은 템플릿 이미지다. 시스템이 알파 채널만 참조하여 색을 결정한다 — 밝은 메뉴바에서는 검정, 어두운 메뉴바에서는 흰색, 선택 시 반전. 따라서 설계 가능한 요소는 실루엣 하나이며 색·그라디언트·굴절은 적용되지 않는다.

A.2.2 형태 설계

실제 물방울은 표면장력과 중력의 결과로 하단이 넓고 평탄하며, 상단이 더 둥글고, 좌우가 완전히 대칭이 아니다. 이 비대칭이 도형과 액체를 구분한다.

후보특성18pt 렌더링 평가

B · 윤곽 + 광점광점이 액체 표면을 표현한다채택 축소 시에도 광점이 유지된다
C · 채움 + 광점 음각시인성이 가장 높으나 메뉴바에서 과중하다존재감 과다
D · 접촉면 표현“유리에 맺힘”의 서사가 가장 강하다선 요소 2개로 축소 시 뭉개진다

A.3

굴절 구현 가능성 검증

결론 — macOS 에는 자신의 창 뒤에 있는 다른 애플리케이션의 화면을 굴절시키는 공개 API 가 존재하지 않는다. 흐림(blur)은 제공되며, 굴절은 제공되지 않는다.

A.3.1 실험 1 — CALayer.backgroundFilters

해당 API 는 레이어 배후 콘텐츠에 Core Image 필터를 적용한다. 창이 투명하면 배후는 다른 창이므로, 동작할 경우 굴절이 성립한다. 격자 무늬 창 위에 CIBumpDistortion 을 적용한 투명 패널을 배치했다.

A.3.2 실험 2 — NSVisualEffectView 및 macOS 26 Liquid Glass

Apple 이 제공하는 유리 재질 2종을 동일 배경에서 비교했다. 굴절은 직선의 변위로만 입증된다 — 흐림·틴트·가장자리 하이라이트는 굴절이 아니다.

즉 Liquid Glass 는 서리 유리이며 렌즈가 아니다.

A.3.3 실험 3 — 자체 캡처 후 왜곡

시스템이 굴절을 제공하지 않으므로, 배후 화면을 직접 취득하여 렌즈 왜곡을 계산해 렌더링하는 방식이 유일한 대안이다. 절차는 다음과 같다.

  1. ScreenCaptureKit 으로 물방울이 점유한 영역을 실시간 캡처한다. 이때 SCContentFilter(display:excludingWindows:) 로 물방울 창 자신을 반드시 제외해야 한다. 미제외 시 무한 되먹임이 발생한다.
  2. 취득한 이미지에 Core Image 로 렌즈 왜곡을 적용한다.
  3. 물방울 형태로 마스킹하고 가장자리 음영·림라이트·하이라이트를 합성한다.
  4. 매 프레임 재렌더링한다.

2~4단계의 광학적 타당성을 먼저 검증했다. 캡처 대신 기존 화면 이미지를 배경으로 동일 파이프라인을 실행했다.

이 값들은 상호 종속적이므로 화면 계층이 아니라 DropletAppearance (순수 함수)에 정의하고 테스트 6건으로 불변식을 검증한다. 최대 크기가 창을 초과하면 가장자리가 절단되며, 절단된 형상은 물방울로 인지되지 않는다.

모션 줄이기 설정은 크기 변화가 아니라 애니메이션을 비활성화한다. 크기는 이 요소의 유일한 상태 신호이므로 제거하면 상태를 인지할 수단이 소멸한다.

A.4.4 상호작용 (R-4)

누름 · 이동 · 탭을 단일 DragGesture(minimumDistance: 0) 로 처리한다. 제스처를 분리하면 탭과 드래그가 상호 간섭한다. 이동 임계값은 3pt 다.

구현 중 확인된 결함

초기 구현은 제스처가 제공하는 translation 으로 창을 이동시켰다. 해당 값은 뷰의 좌표계를 기준으로 산출되는데, 창을 이동시키면 뷰도 함께 이동하여 이동량이 상쇄된다. 967pt 를 드래그했을 때 창은 483pt 만 이동했다 — 정확히 절반이다. 화면 좌표(NSEvent.mouseLocation)를 직접 참조하는 방식으로 변경하여 해소했다. AppKit 의 창 드래그와 동일한 방식이며 되먹임이 발생하지 않는다.
