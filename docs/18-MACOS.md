# macOS 앱

> 화면에 떠 있는 물방울에 스크린샷을 끌어다 놓으면 캘린더까지 간다.
> 2026-08-01 · 실제로 끝까지 돌려서 확인함

---

## 0. 왜 다르게 만들었나

같은 제품이지만 **쓰는 방식이 다르다.**

| | iOS | macOS |
| --- | --- | --- |
| 들어오는 길 | 공유 시트 · 사진 고르기 | **물방울에 끌어다 놓기** · 다른 앱으로 열기 · 파일 고르기 |
| 확인 | 확인 화면을 **반드시** 거친다 | 분명하면 **바로 넣고 되돌릴 수 있게** |
| 목록 | 지갑 스타일 겹침 스택 | 평범한 목록 |
| 상시 존재 | 앱을 연다 | 메뉴바 + 떠 있는 물방울 |

폰에서는 한 손으로 몇 번 탭하는 것이 자연스럽고, 맥에서는 **끌어다 놓는 것**이 자연스럽다.
화면이 넓고 포인터가 정확하니 겹쳐 쌓을 이유도 없다.

**공유하는 것과 안 하는 것**

```
공유한다   Models · Services · Store · Shared   (코드 수정 0)
안 한다    Views                                (화면은 플랫폼마다 다른 것이 맞다)
```

`VisionOCRService` 만 손봤다. `UIImage` 를 쓰고 있었는데 ImageIO 의 `CGImageSource` 로 바꿨다 —
`UIImage`/`NSImage` 는 플랫폼마다 다르지만 `CGImage` 는 어디서나 같다.

## 1. 물방울

```
        ╭───────╮
       │    ○    │   68 × 68 · 가운데는 완전히 투명
        ╰───────╯
     화면 오른쪽 아래에 떠 있다
```

**가운데는 아무것도 그리지 않는다.** 뒤 화면이 흐려짐 없이 그대로 보인다.

처음에는 `.ultraThinMaterial` 로 채웠는데, 그건 뒤를 **흐리게** 만드는 재질이라
물방울 자리에 뿌연 판이 생겼다. 게다가 macOS 에서는 그 흐림이 원 밖으로 번져
**네모난 자국**으로 보였다. 투명하게 하려면 채우는 방법을 고를 게 아니라
**채우지 않는 것**이 답이었다.

`NSHostingView` 의 배경도 함께 비워야 한다. 창을 투명하게 해도 안쪽 뷰가 칠하면 소용없다.

### 그래도 네모가 남았다 — 그림자였다

채움을 없앤 뒤에도 뿌연 네모가 보였다. 창이 그리는 것만 따로 떠서 **알파 채널**을
찍어 보니 원인이 보였다.

```
------*###*------------.......................------------####------   ← 모서리에 옅은 층
###+------.................................................------###   ← 가운데는 알파 0
```

가운데는 완전히 투명한데 **네 모서리에 옅은 층**이 있었다. `.shadow(radius: 3)` 이다.

창이 고리에 딱 맞는 68 × 68 이라 **중심에서 모서리까지(48pt)가 고리 반지름(34pt)보다
가깝다.** 그림자가 모서리에 닿고, 창 경계에서 직선으로 잘린다. 그 잘린 직선이 네모다.

> 눈으로는 "흐릿하다"까지만 보인다. 무엇이 흐린지는 알파 채널을 찍어야 알 수 있었다.

그림자를 없애고, 윤곽은 **원 밖으로 한 픽셀도 넘지 않는** 실선으로 만들었다.

**스테인리스처럼 보이게 하는 것**

| 각도 그라디언트 | 둘레를 돌며 밝은 띠와 어두운 띠가 번갈아 온다. 금속은 한 방향에서만 빛나지 않는다 |
| 큰 명암 차 | 어두운 띠가 `0.22`. 처음엔 `0.45` 였는데 흰 배경에서 그냥 흰 고리로 보였다 — 금속의 어두운 부분은 회색이 아니라 거의 검다 |
| 바깥 윤곽선 | 밝은 배경에서도 배경에 묻히지 않게. 그림자가 하던 일을 번지지 않고 한다 |
| 안쪽 모서리 검은 선 | 그늘. 두께가 있다는 신호 |

크기는 68pt다. 떠 있는 것은 작을수록 좋지만, 너무 작으면 드롭 목표로 맞히기 어렵다.

| 상태 | 보이는 것 |
| --- | --- |
| 평소 | 금속 고리만. 가운데는 뚫려 있다 |
| 끌고 오는 중 | **카메라 셔터가 닫히듯 조인다** — 두께가 안쪽으로 자라 구멍이 좁아지고, 강조색이 그 가장자리에 뜬다 · 물결이 안쪽으로 모인다 |
| 읽는 중 | 회전자 |

**색만 바꾸지 않는다** — 구멍 크기가 함께 바뀐다 (CLAUDE 규칙 13).
모션 줄이기를 켜면 물결과 지름 변화가 사라지고 구멍만 좁아진다.

### 조여도 드롭 영역은 그대로다

작아지는 것은 **고리뿐이다.** 프레임과 드롭 영역은 68pt 그대로 둔다.

겨냥하는 중에 목표가 작아지면 커서가 밖으로 나가 놓기가 풀리고, 풀리면 다시 커지고,
커지면 또 들어온다. **깜빡임이 된다.** 그래서 `scaleEffect` 는 고리에만 걸고
`contentShape` 위에는 걸지 않는다.

### 왜 `NSPanel` 인가

SwiftUI 의 `Window`/`WindowGroup` 으로는 이 조합을 만들 수 없다.

| `.nonactivatingPanel` | 물방울을 눌러도 **작업하던 앱이 뒤로 가지 않는다.** 그 앱에서 그대로 끌어와야 한다 |
| `.floating` | 다른 창 위에 떠 있는다 |
| `canJoinAllSpaces` | 데스크톱을 바꿔도 따라온다 |
| 투명 배경 | 원 밖의 사각형이 보이지 않는다 |

위치는 사용자가 옮기면 기억한다 (`setFrameAutosaveName`).

## 2. 바로 넣기 — 그리고 되돌리기

**"AI 결과는 제안이다"(ADR-4)를 버리지 않았다.** 두 갈래로 나눴을 뿐이다.

```
분명할 때   바로 넣는다  →  "넣었어요 · 실행 취소 · 고치기" 배너 (8초)
모호할 때   확인 창을 연다
```

확인 화면은 **저장 전에** 사람을 세우고, 되돌리기는 **저장 후에** 결정권을 남긴다.
둘 다 사람이 최종 판단을 하고, 다른 것은 속도뿐이다.

> **그래서 실행 취소가 반드시 있어야 한다.** 없으면 그냥 조용한 자동 저장이 된다.

### 판정 — `AutoFilePolicy`

```
날짜 없음                  →  물어본다 ("날짜를 찾지 못했어요")
ambiguities 있음           →  물어본다 (그 모호점을 그대로 보여준다)
confidence < 0.80          →  물어본다
그 밖                      →  바로 넣는다
```

**`ambiguities` 를 `confidence` 보다 먼저 본다.** 실제 호출에서 confidence 가
0.9~1.0 으로만 나와 눈금 역할을 못 하기 때문이다([12장 §3](12-IMPLEMENTATION-READINESS.md)).
지금 실제로 거르고 있는 것은 `ambiguities` 쪽이다.

### 되돌리기가 하는 일

할 일과 **캘린더 일정을 둘 다** 거둔다. 하나만 지우면 사용자는
"취소했는데 일정이 그대로"인 상태를 보게 된다.

## 3. 들어오는 길 네 가지

| 길 | 되나 | 비고 |
| --- | --- | --- |
| 물방울에 끌어다 놓기 | ✅ | 주 경로 |
| 파인더 "다른 앱으로 열기" | ✅ | 실제로 끝까지 확인함 |
| 앱 아이콘에 끌어다 놓기 | ✅ | 같은 경로 (`CFBundleDocumentTypes`) |
| 메뉴바 → 파일에서 고르기 | ✅ | 끌어다 놓기를 모르는 사용자용 |
| **공유 메뉴** | 🟡 | 파일 URL 로 오는 공유만. 아래 참고 |

### 공유 확장의 제약

확장은 **파일 URL 만 받는다.** 그래서 App Group 이 필요 없다.

`NSWorkspace.open(url)` 로 앱을 열면 LaunchServices 가 **앱에게 그 파일의 샌드박스
확장을 준다** — "다른 앱으로 열기"와 정확히 같은 길이다. 확장이 파일을 복사할 필요가 없고,
따라서 앱과 확장이 공유하는 저장소도 필요 없다.

이미지 **데이터**로 오는 공유(예: 사파리에서 이미지 복사)는 받지 않는다.
그건 확장이 어딘가에 써 두고 앱이 읽어야 하는데, macOS 의 App Group 은
**팀 식별자 접두사를 요구한다** — iOS 의 S-1.3 과 같은 제약이다.

## 4. 샌드박스

| entitlement | 왜 |
| --- | --- |
| `app-sandbox` | 배포 요건 |
| `network.client` | 백엔드를 부른다 |
| `files.user-selected.read-only` | **사용자가 고르거나 끌어다 놓은 파일만** 읽는다 |
| `personal-information.calendars` | 캘린더에 넣는다 |

**샌드박스가 실제로 막는 것을 확인했다.** 검증하려고 `CAPTURETASK_FILE` 로 임의 경로를
넘겼더니 `Operation not permitted (Code=257)` 이 났다. 하드코딩한 경로는 "사용자가 고른 것"이
아니기 때문이다 — 정상 동작이다. 실제 드롭과 파일 고르기는 샌드박스 확장을 함께 받는다.

> DEBUG 로 확인할 때는 컨테이너 안에 두면 된다.
> `~/Library/Containers/com.example.capturetask.mac/Data/Documents/`

## 5. 빌드·실행·확인

```bash
xcodegen generate
xcodebuild build -project CaptureTask.xcodeproj -scheme CaptureTaskMac -derivedDataPath build
open build/Build/Products/Debug/CaptureTaskMac.app
```

`./scripts/verify.sh` 가 macOS 빌드도 함께 돌린다. 공유 코드를 고치면 여기가 먼저 깨지는데,
빌드하지 않으면 그 사실을 아무도 모른 채 초록이 난다.

### 끌어다 놓기 없이 주 경로 확인하기

끌어다 놓기는 자동화할 수 없다. DEBUG 전용 경로를 뒀다.

```bash
cp <이미지> ~/Library/Containers/com.example.capturetask.mac/Data/Documents/shot.png
CAPTURETASK_FILE=~/Library/Containers/com.example.capturetask.mac/Data/Documents/shot.png \
  build/Build/Products/Debug/CaptureTaskMac.app/Contents/MacOS/CaptureTaskMac
```

또는 실제와 같은 길로:

```bash
open -a build/Build/Products/Debug/CaptureTaskMac.app <이미지>
```

## 6.5 앱 아이콘

물방울 안으로 할 일 세 개가 사방에서 빨려 들어간다 — 이 제품이 하는 일 그대로다.
흩어져 있던 것(스크린샷)이 한 곳으로 모여 정리된다.

```bash
swift scripts/icon/MakeIcon.swift <출력폴더>
```

손으로 그리지 않고 스크립트로 짓는 이유 — 색이나 각도를 고칠 때 모든 크기를 다시
만들어야 하는데, 손으로 하면 어느 크기 하나가 반드시 옛것으로 남는다.

**막대를 물방울보다 먼저 그린다.** 밖에서 안으로 가로지르게 하고 그 위에 반투명한
유리를 덮으면 안쪽 부분이 물속에 잠긴 것처럼 보인다 — 그게 "들어간다"는 그림이다.
유리 안에 가둬 그리면 그냥 무늬가 된다.

**유리는 파랑이 아니라 흰색 계열이다.** 파란 유리를 씌웠더니 노란 막대가
올리브색으로 죽었다 — 보색이 상쇄된다.

### 겪은 함정 — 요청한 것의 두 배가 나온다

`NSImage.lockFocus()` 는 Retina 화면의 배율(2x)을 적용한다. 1024를 요청했는데
2048이 나왔고 Xcode 가 아이콘을 거부했다. `rep.size` 를 고쳐도 픽셀 수는 그대로다.

`CGContext` 를 직접 만들어 픽셀 수를 못 박았다. `noneSkipLast` 로 **알파 없는**
비트맵을 만드는 것도 함께 해결된다 — iOS 앱 아이콘은 투명도를 가질 수 없는데,
`NSBitmapImageRep` 는 알파 없는 그리기 문맥을 만들지 못한다.

생성기가 요청 크기와 다르면 **그대로 내보내지 않고 멈춘다.** 한 번 이걸로 거부됐다.
