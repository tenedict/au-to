# Engineering Playbook

> [obra/superpowers](https://github.com/obra/superpowers) 방법론을 이 프로젝트에 맞게 적용한 문서.
> BMAD 가 **무엇을 만들지(산출물)** 를 정한다면, 이 문서는 **어떻게 만들지(규율)** 를 정한다.
> 두 층은 겹치지 않는다. BMAD 문서를 다 써도 이 규율이 없으면 코드는 여전히 엉망이 된다.

## 0. 두 층의 관계

```
┌─ BMAD 층 (무엇을) ──────────────────────────────────┐
│  Brief → PRD → SRS → UX → SPEC → Architecture →    │
│  Epics/Stories → Readiness Gate → Sprint            │
└────────────────────────────────────────────────────┘
                       ↓ 스토리 하나를 집어들면
┌─ Superpowers 층 (어떻게) ───────────────────────────┐
│  브레인스토밍 → 계획(2~5분 태스크) → 🔴🟢🔵 TDD →    │
│  검증 → 코드 리뷰 → 마무리                            │
└────────────────────────────────────────────────────┘
```

## 1. 브레인스토밍 — 코드를 쓰기 전에

**원칙: 요구를 받자마자 코드를 쓰지 않는다.**

| 단계 | 하는 일 |
| --- | --- |
| 1 | 요구를 **되묻는다** |
| 2 | 설계를 **한 덩어리씩** 제시한다. 한 번에 전부 내밀면 검토받지 못한다 |
| 3 | 각 덩어리마다 확인을 받고 넘어간다 |

### 실전 사례 — 캘린더 뷰 (S-7)

"캘린더에서도 볼 수 있게 캘린더 뷰도 필요할까?" 라는 요구에서 되물어 갈린 결정들:

- **앱 안 캘린더에서 할 일을 고칠 수 있나?** → 아니오. 읽기 전용.
  *두 곳에서 고칠 수 있으면 "어느 쪽이 진짜인가"를 사용자도 코드도 답하지 못한다.*
- **Apple 캘린더가 이미 캘린더인데 왜 또?** → 앱을 나가지 않게 하는 정도만.
  그래서 월 격자 하나뿐이고 주/일 뷰는 없다.
- **완료한 할 일도 격자에 보이나?** → 보인다. 달력에서는 "그날 뭘 했더라"가 더 자주 필요하다.
  단, 점(마감 표시)은 **미완료만** 센다.

이 셋을 안 물었으면 셋 다 틀리게 만들었을 것이다.

## 2. 계획 — 2~5분짜리 태스크로 쪼갠다

**한 태스크의 조건**

- [ ] 2~5분 안에 끝난다
- [ ] **어느 파일의 어느 함수**를 건드리는지 적혀 있다
- [ ] **어떻게 검증**하는지 적혀 있다
- [ ] 앞 태스크가 끝나야 시작할 수 있는지가 분명하다

### 나쁜 태스크 vs 좋은 태스크

| ✕ | ○ |
| --- | --- |
| "마감 알림 구현" | 1. `ReminderPlan`·`ReminderKind` 타입 (1분)<br>2. `ReminderSchedule.plans` 순수 함수 (5분)<br>3. 시각 계약 테스트 10건 — RED 확인 (5분)<br>4. `TaskReminderScheduling` 프로토콜 + `LocalNotificationService` (5분)<br>5. `TaskStore` 저장·완료·삭제에 재예약 연결 (5분)<br>6. 확인 화면에 실제 예약 시각 문구 (3분)<br>7. 시뮬레이터에서 확인 화면 문구 확인 (2분) |

쪼개는 이유는 관리가 아니라 **누락 방지**다. "마감 알림 구현"이라고 적었으면
완료·삭제 시 취소를 넣었는지 아무도 모른다.

계획의 실물은 [11-EPICS-STORIES.md](11-EPICS-STORIES.md) 와 [plans/](plans/) 에 있다.

## 3. TDD — 🔴 RED → 🟢 GREEN → 🔵 REFACTOR

계산·규칙·불변 조건이 걸린 변경은 **예외 없이** 이 순서다.

```
🔴 RED     실패하는 테스트를 먼저 쓴다 → 실제로 실패하는 것을 눈으로 본다
🟢 GREEN   통과시키는 최소한의 코드를 쓴다
🔵 REFACTOR 초록을 유지하며 정리한다
```

### 의무 영역

- 마감 묶음 분류와 정렬
- 알림 시각 계산과 식별자
- 초안 확인 필요 판정
- 저장·복원과 버전 이동
- 백엔드 요청 계약과 응답 검증
- 캡처 삭제 조건

**왜 이것들인가** — 전부 "화면에서는 맞아 보이는데 틀린" 부류다.
지난 마감이 하나 아래로 밀려 있어도, 알림이 한 시간 늦어도 눈으로는 모른다.

### RED 를 눈으로 보는 것이 중요한 이유

Sprint 1 에서 저장 왕복 테스트가 실패했다. 출력된 두 값은 **글자 그대로 똑같아 보였다.**
ISO 8601 이 초 미만을 버리기 때문이었다. RED 를 안 봤으면 "왜 통과하지" 를 못 물었을 것이다.

## 4. 체계적 디버깅 — 30분 규칙

30분 넘게 막히면 **찍어보기를 멈춘다.**

| 단계 | 하는 일 |
| --- | --- |
| 1 · 재현 | 가장 작은 경로로 재현한다 |
| 2 · 좁히기 | 범위를 절반씩 줄인다 |
| 3 · 근본 원인 | "무엇이 잘못됐나"가 아니라 **"왜 그렇게 동작하나"** 까지 간다 |
| 4 · 증명 | 재현 테스트를 쓰고, 고친 뒤 전체 스위트로 확인한다 |

### 실전 사례 — 사라지는 App Group

**증상** — entitlements 에 App Group 을 써 넣었는데 빌드하면 다시 빈 `<dict/>`.

- ❌ 찍어보기: "Xcode 가 캐시하나?" "권한 문제인가?"
- ✅ 좁히기: 파일을 고친다 → 확인(있음) → `xcodegen generate` → 확인(없음)
- ✅ 근본 원인: XcodeGen 은 `entitlements` 에 `properties` 가 없으면 파일을 **생성**한다.
  `path` 만 있으면 빈 dict 로 만든다
- ✅ 증명: `project.yml` 에 `properties` 로 옮기고 generate 후 확인.
  프로젝트 규칙 1에 `project.yml` 검사를 추가

**"파일을 고쳤는데 왜 원래대로 돌아가지"는 거의 언제나 그 파일이 생성물이라는 뜻이다.**

## 5. 완료 전 검증

**구현했다 ≠ 완료했다.**

```bash
./scripts/verify.sh
```

사람·Claude·Git Hook·CI 가 모두 이 명령 하나를 쓴다. 각자 다른 명령을 쓰면
"내 쪽에서는 됐는데"가 생긴다.

### 완료의 정의

1. 수용 기준을 **항목별로** 확인했다
2. 새 테스트의 RED 를 눈으로 봤다
3. `verify.sh` 가 초록이다
4. 빌드 경고 0
5. 시뮬레이터에서 직접 눌러 봤다
6. 문서와 코드가 어긋난 곳이 없다 ([08장](08-와이어프레임.md) 대응표)
7. **확인 못 한 항목을 확인 못 했다고 적었다**

### 규칙이 확인하지 못하는 것

규칙은 grep 이다. **"어떤 글자가 어디 있는가"까지만 답할 수 있다.**

프로젝트 규칙 1은 App Group 식별자가 네 곳에서 같은지 본다. 하지만 그 그룹이
실제 개발자 계정에 등록됐는지는 모른다 — 실기기에서 공유 시트를 눌러 봐야 안다.

> **규칙 통과 ≠ 올바름.** 규칙은 문법과 구조를 본다. 올바름은 테스트만 본다.
> 실기기에서만 드러나는 것은 사람만 본다.

### 새 규칙을 넣을 때

**일부러 어겨 보고 빨간불과 종료 코드 1을 확인한 뒤에 커밋한다.**
안 잡히는 규칙은 초록불만 부풀린다 — 검사기가 본다고 믿고 사람이 안 보게 되기 때문에
**있는 것이 없는 것보다 나쁘다.**

## 6. 코드 리뷰 — 2단계

순서를 지킨다. 1이 틀렸는데 2를 보면 시간만 쓴다.

### 1단계 · 명세 준수

- 캡처가 유실될 수 있는 경로가 생겼나?
- 확인 화면을 지나지 않는 저장 경로가 생겼나?
- 낮은 신뢰도가 캘린더에 쓰일 수 있나?
- 알림 취소 지점이 늘었나?
- 새 저장 필드가 옵셔널인가? 구버전 디코딩 테스트가 있나?
- 파생 값을 저장하기 시작했나?

### 2단계 · 코드 품질

- 의존 방향 (Model 이 무언가를 알게 됐나)
- 계산이 뷰로 새지 않았나
- 이름 — [05-IA.md §9](05-IA.md) 용어 사전
- 접근성 — 색만으로 정보를 전달하나, 비활성에 이유가 있나
- 프라이버시 — 로그에 원문이 남나

## 7. 마무리

- 커밋: Conventional Commits · 한 커밋에 하나의 검토 가능한 관심사
- 관련 테스트가 초록일 때만 커밋
- 푸시 전 `./scripts/verify.sh` 전체
- 생성물(`build/`, `.xcodeproj`)과 비밀(`.env`)은 커밋하지 않는다
- **커밋 기록에는 사람만 남는다.** AI 협업자 트레일러는 훅이 지우고 CI 가 강제한다

## 8. AI 에이전트에게 맡길 때

| 규칙 | 왜 |
| --- | --- |
| 시작 전에 [`project-context.md`](project-context.md) 를 준다 | 프로젝트 판단 기준을 공유한다 |
| 코드를 쓰기 전에 계획을 받는다 | 큰 제목 하나가 여러 쓰기 경로를 숨긴다 |
| 완료 보고에 **숫자**를 요구한다 | "테스트 통과" 는 몇 건인지 말하지 않는다 |
| 실행하지 않은 결과를 보고하면 되돌린다 | "아마 될 거예요" 는 검증이 아니다 |
| 확인 못 한 항목을 ✅/⚠️ 로 나누게 한다 | 뭉뚱그린 완료 보고가 가장 큰 손해다 |

### 보고 형식

```
✓ 프로젝트 규칙 통과 · iOS 115/115 · 백엔드 46/46 · 빌드 경고 0
⚠️ 공유 시트 경로는 실기기가 필요해 확인하지 못했습니다 (M-1)
```
