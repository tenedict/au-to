> [17장](17-ONDEVICE-LLM-RESEARCH.md)이 **무엇을 쓸지** 고른 문서라면,

> 2026-08-03 · 구현은 이미 있고(`OnDeviceContextUnderstandingService`), 켜지 않았을 뿐이다.

## 0. 네 줄 요약

1. **작은 모델을 크게 만들려 하지 말고, 과제를 작게 만들어라.** 3B 모델이 못 하는 것은
   추론이 아니라 **한 번에 여러 가지를 하는 것**이다.
2. **날짜 계산을 모델에게 시키지 마라.** 지금 우리가 그러고 있고, 이게 온디바이스에서
   가장 먼저 무너질 자리다. 모델은 "다음 주 화요일"을 **가리키게만** 하고 날짜는
   Swift 가 센다.
3. **켜고 끄는 스위치가 아니라 라우터가 필요하다.** 쉬운 것은 기기가, 어려운 것은
   서버가 한다. 판정은 순수 함수여야 하고 그래야 테스트가 닿는다.
4. **온디바이스로 옮기는 근거는 프라이버시가 아니라 원가다.** 프라이버시는 결과이고,
   무료 등급을 성립시키는 것은 한계 원가 0 이다.

## 1. 지금 코드가 실제로 하는 일

`OnDeviceContextUnderstandingService` 는 이미 다 만들어져 있다.

```
OCR 텍스트 + 지금 시각 + 시간대
   → LanguageModelSession(instructions:)
   → @Generable OnDeviceTaskList          (guided generation 이 모양을 강제)
   → OnDeviceTask.makeDraft()              (여기서 한 번 더 검증)
   → [TaskDraft]
```

잘 되어 있는 것 셋을 먼저 적는다. **바꾸면 안 되는 것들**이다.

| | 왜 옳은가 |
| --- | --- |
| `@Generable` + `@Guide` | 모양을 **제약 디코딩**으로 강제한다. 파싱 실패가 구조적으로 없다 |
| `dueDate` 를 옵셔널이 아닌 **빈 문자열**로 | 작은 모델은 `null` 을 자주 틀린다. 주석에 이미 적혀 있다 |
| `parseDate` 가 오프셋 없는 형식도 받음 | 작은 모델은 타임존을 자주 빠뜨린다 |

**이미 작은 모델의 실패 방식을 알고 짠 코드다.** 아래 제안은 이 위에 얹는 것이다.

## 2. 가장 큰 문제 — 모델에게 달력을 시키고 있다

지금 프롬프트는 이렇게 말한다.

```
지금: 2026-08-03T02:00:00+09:00
시간대: Asia/Seoul
원문: 다음 주 화요일까지 서류 제출해 주세요
```

그리고 모델에게 `dueDate: "2026-08-11T00:00:00"` 를 **직접 쓰라고** 한다.

이 한 줄이 모델에게 시키는 일을 풀어 보면 이렇다.

1. "다음 주" 가 어느 주인지 판정 (이번 주 기준? 다음 월요일 기준?)
2. 그 주의 화요일이 며칠인지 **계산**
3. 월말·윤년·주 경계 처리
4. ISO 8601 문자열로 **직렬화**

**2·3·4 는 산수다.** 큰 모델은 이걸 외워서 맞히지만 3B 모델은 조용히 틀린다.
게다가 틀려도 형식은 완벽하다 — guided generation 이 모양을 보장하기 때문이다.
**형식이 맞으니 아무도 못 잡는다.** 이게 온디바이스 전환에서 가장 위험한 실패다.

### 고치는 방향 — 모델은 가리키고, Swift 가 센다

```
지금 (모델이 계산)              바꾼 뒤 (모델이 가리킴)
────────────────────           ──────────────────────
dueDate: "2026-08-11"          anchor: .nextWeek
                               weekday: .tuesday
                               timeOfDay: none
                               quote: "다음 주 화요일"
                                  ↓
                               Swift: Calendar 로 계산
```

`@Generable` 은 열거형도 강제할 수 있다. 모델이 고를 수 있는 값을 우리가 정하면
"2026-13-45" 같은 것이 **나올 수 없게** 된다.

| 무엇이 좋아지나 | |
| --- | --- |
| 산수 오류가 사라진다 | `Calendar` 는 윤년도 주 경계도 안다 |
| 테스트가 닿는다 | 상대 표현 → 날짜는 순수 함수가 된다. `now` 를 인자로 받는다 (규칙 10) |
| 두 엔진이 같아진다 | 백엔드도 같은 후처리를 쓰면 평가셋 결과가 서로 비교 가능해진다 |
| 모델을 바꿔도 안 깨진다 | 모델은 분류만 하고, 분류는 모델 크기에 덜 민감하다 |

**이건 온디바이스만을 위한 변경이 아니다.** [19-EVAL](../engineering/19-EVAL.md)이
"상대 날짜" 를 별도 범주로 나눠 재고 있는 것 자체가, 이 자리가 이미 취약하다는
신호였다.

> 절대 날짜("8월 12일 오후 3시")는 지금처럼 그대로 받아도 된다.
> 산수가 없기 때문이다. **상대 표현만** 이 구조로 옮긴다.

## 3. 한 번에 하나씩 시킨다

지금은 한 번의 호출에서 여섯 가지를 동시에 요구한다.

```
할 일 찾기 · 여러 개로 쪼개기 · 제목 짓기 · 날짜 계산
· 신뢰도 매기기 · 모호점 적기
```

큰 모델은 된다. 3B 는 **하나를 잘하면 다른 하나를 놓친다.**

### 두 단계로 나눈다

```
1단계  분할   "이 텍스트에 일정이 몇 개이고 각각 어느 구절인가"
              → [구절] 만 돌려준다. 날짜도 제목도 아직 없다

2단계  추출   구절 하나에 대해서만 제목 · 앵커 · 시각 · 모호점
              → 구절마다 한 번씩
```

**대부분의 캡처는 일정이 하나다.** 그러면 1단계가 거의 즉시 끝나고 2단계도 한 번이다.
비용은 여러 개일 때만 늘어나는데, 그때는 정확도가 훨씬 중요하다.

| | 지금 | 나눈 뒤 |
| --- | --- | --- |
| 일정 1개 | 호출 1회 | 호출 2회 (둘 다 짧다) |
| 일정 3개 | 호출 1회 · 뒤쪽 일정의 품질이 떨어짐 | 호출 4회 · 각각 온전함 |

온디바이스는 **호출당 요금이 없다.** 나누는 비용이 지연뿐이고, 지연은 어차피
백그라운드다 (`CaptureQueue`). 이 교환은 온디바이스에서만 성립하고,
그래서 백엔드와 다른 전략을 써도 된다.

## 4. 라우터 — 어디로 보낼지 정하는 순수 함수

"온디바이스로 바꾼다" 가 아니다. **어느 것을 기기가 하고 어느 것을 서버가 하는가**다.

```swift
/// 이 텍스트를 어디서 읽을 것인가. 순수 함수여야 테스트가 닿는다.
enum AnalysisRoute { case onDevice, backend }

struct AnalysisRouter {
    static func route(
        for text: String,
        deviceAvailable: Bool,
        userPrefersPrivacy: Bool,
        isMetered: Bool
    ) -> AnalysisRoute
}
```

### 판정의 순서

| 순서 | 조건 | 결과 | 왜 |
| --- | --- | --- | --- |
| 1 | 기기가 못 쓴다 | 서버 | 다른 선택지가 없다 |
| 2 | 사용자가 "기기에서만" 을 켰다 | 기기 | 사용자의 뜻이 우선이다. 못 하면 **못 했다고 말한다** |
| 3 | 무료 등급 · 이번 달 한도 초과 | 기기 | 온디바이스가 무료 등급을 성립시킨다 |
| 4 | 텍스트가 길거나 복잡하다 | 서버 | §5 의 신호 |
| 5 | 그 밖 | 기기 | 기본은 기기다 |

**2번을 켠 사용자에게 조용히 서버를 쓰지 않는다.** 이건 기능이 아니라 약속이다.
`RuleBasedContextUnderstandingService` 주석에 이미 같은 판단이 적혀 있다 —
*"조용히 품질이 낮은 결과를 내주면 사용자는 AI가 나빠졌다고 생각하고,
우리는 백엔드가 죽은 줄 모른다."*

### 되돌아가기(fallback)는 조용하면 안 된다

```
기기가 실패  →  서버로 다시  →  결과는 나온다
                              →  하지만 우리는 "기기가 얼마나 자주 실패하는지" 를 모르게 된다
```

되돌아갈 때는 **반드시 센다.** 그 숫자가 온디바이스를 기본값으로 올릴지 말지의
유일한 근거다.

## 5. 언제 서버로 보낼 것인가 — 어려움을 재는 신호

모델에게 "어려우세요?" 라고 묻지 않는다. `confidence` 가 눈금 역할을 못 한다는 것을
[19-EVAL §4](../engineering/19-EVAL.md)에서 이미 확인했다 — 실제 호출에서
0.9~1.0 으로만 나왔다.

**텍스트 자체에서 재는 신호**를 쓴다. 전부 순수 함수이고 모델을 부르기 전에 계산된다.

| 신호 | 어려움을 뜻하는 이유 |
| --- | --- |
| 길이 > 400자 | 공지문 전체. 일정이 여럿일 확률이 높다 |
| 날짜처럼 보이는 표현이 3개 이상 | 어느 것이 마감인지 골라야 한다 |
| 상대 표현 + 절대 표현이 섞임 | "8월 12일 검진, 3개월 뒤 재방문" |
| 표·목록 구조 (줄바꿈 + 콜론이 반복) | OCR 이 레이아웃을 잃어버렸을 수 있다 |
| 한 문장에 시각이 둘 (`14:00~16:00`) | 시작인가 마감인가 |

이 신호들은 **온디바이스가 있든 없든 쓸모가 있다** — 백엔드에서도 어려운 것에만
더 큰 모델을 쓰면 되기 때문이다. 그래서 라우터를 먼저 만드는 것이 손해가 아니다.

## 6. 품질을 어떻게 확인할 것인가

### 지금 평가셋으로는 부족하다

15건이다. [19-EVAL §2](../engineering/19-EVAL.md)가 스스로 "기준선으로 쓰기에 작다"
고 적어 두었다. 온디바이스를 켜는 결정은 **15건으로 내리면 안 된다.**

### 필요한 것

| | 지금 | 필요 |
| --- | --- | --- |
| 케이스 수 | 15 | **80~120** |
| 범주 | 명확 · 상대 · 모호 | + 여러 일정 · OCR 잡음 · 함정(일정 아님) |
| 실행 | 백엔드만 | **두 엔진 같은 셋** |

**OCR 잡음 범주가 특히 빠져 있다.** 지금 평가셋은 깨끗한 텍스트를 넣는데,
실제 입력은 Vision 이 뱉은 것이다 — 줄이 섞이고, 글자가 틀리고, 표가 무너진다.
작은 모델은 잡음에 훨씬 약하다. **여기서 갈릴 것이다.**

함정 케이스도 필요하다 — 광고 문자, 배송 완료 알림처럼 **날짜는 있는데 할 일이
없는 것.** 지어내지 않는지를 보는 유일한 방법이다.

### 두 엔진을 나란히 재는 방식

```bash
node server/eval/run.mjs --engine backend    # 지금 있다
swift run OnDeviceEval                        # 필요하다 (iOS 26 기기에서만 돈다)
```

온디바이스 평가는 **기기에서 돌아야 한다.** CI 에서 못 돈다는 뜻이고,
그래서 `verify.sh` 에 넣지 않는다 — 넣으면 CI 가 언제나 그 검사를 건너뛰고,
건너뛴 검사는 초록불을 거짓말로 만든다.

### 켜도 되는 조건

| 항목 | 문턱 |
| --- | --- |
| 명확 · 절대 날짜 | 백엔드와 **동률** |
| 상대 날짜 | 백엔드의 95% 이상 (§2 를 고친 뒤라면 동률이어야 한다) |
| 지어내기 (함정 케이스) | **백엔드보다 나쁘면 안 된다.** 이건 타협 대상이 아니다 |
| p95 지연 | 4초 이내 |

**지어내기만은 절대 기준이다.** 다른 항목이 다 좋아도 이게 나빠지면 켜지 않는다.
없는 일정을 만들어 캘린더에 넣는 것은 못 넣는 것보다 나쁘다.

## 7. 기기에서만 생기는 문제들

### 발열과 전력

`CaptureQueue` 가 이미 한 번에 하나씩만 돌린다. 이게 온디바이스에서는 **성능
설계이기도 하다** — 병렬로 돌리면 Neural Engine 경합으로 전체가 느려지고
기기가 뜨거워진다.

`IntakeRate` 의 1분 10건 제한도 그대로 쓸모가 있다. 클라우드에서는 **요금** 때문이었고
기기에서는 **발열** 때문이다. 같은 값이 두 이유를 다 막는다.

### 첫 호출이 느리다

모델을 메모리에 올리는 시간이 있다. 사용자가 처음 담을 때 이게 그대로 지연이 된다.

앱이 앞으로 나올 때 세션을 미리 만들어 둔다 (`prewarm`). 다만 **쓰지도 않을
세션을 매번 만들지 않는다** — 배터리를 먹는다. 최근에 담은 적이 있는 사용자에게만
미리 만든다.

### 모델이 조용히 바뀐다

OS 업데이트로 모델이 바뀌면 어제 잘 되던 것이 오늘 틀릴 수 있다.
**우리 앱 버전과 무관하게** 일어난다.

| 대비 | |
| --- | --- |
| 시스템 모델 버전을 기록에 남긴다 | 정정률이 튀었을 때 원인을 찾을 수 있다 |
| 평가를 릴리스마다 다시 돌린다 | 우리가 안 바꿔도 결과는 바뀐다 |

### 컨텍스트 한도

Foundation Models 의 창은 크지 않다. 긴 공지 전체를 넣으면 잘린다.
`instructions` 도 그 예산을 먹는다.

지금 지시문은 열 줄이다. §3 처럼 단계를 나누면 각 단계의 지시문이 **더 짧아진다** —
나누는 것이 컨텍스트 예산에도 이득이다.

## 8. 무엇을 하지 말 것인가

| 하지 마라 | 왜 |
| --- | --- |
| **모델을 직접 싣기 (MLX · llama.cpp)** | 1.5GB 를 더 받게 하는 대가로 얻는 것이 무엇인지 답이 없다 ([17장 §2](17-ONDEVICE-LLM-RESEARCH.md)) |
| **파인튜닝** | 평가셋이 15건이다. 무엇에 맞출지 모르는 상태에서 맞추는 것은 과적합이다 |
| **온디바이스를 기본값으로 먼저 켜기** | iPhone 15 Pro 미만은 여전히 서버가 필요하다. 기본을 바꾸면 그 사용자들이 조용히 다른 경험을 한다 |
| **프라이버시를 이유로 서둘러 켜기** | 정확도가 떨어진 프라이버시는 팔리지 않는다. 순서는 정확도 먼저다 |
| **`confidence` 로 라우팅하기** | 눈금 역할을 못 한다는 것을 이미 측정했다 ([19-EVAL §4](../engineering/19-EVAL.md)) |

| **2** | 날짜를 앵커+요일로 (§2). 백엔드도 함께 | 두 엔진 공통 이득. 여기가 가장 큰 개선 | 1~2주 |
| **3** | 온디바이스 평가 러너 (기기에서 도는) | 3번 없이는 4번의 판단 근거가 없다 | 며칠 |
| **4** | 두 단계 분할 (§3) — 온디바이스만 | 호출당 요금이 없어야 성립하는 전략 | 1주 |
| **5** | `AnalysisRouter` + 되돌아가기 계수 | 켜는 것이 아니라 **섞는** 것 | 1주 |
| **6** | 설정에 "기기에서만" 켜기 (기본 꺼짐) | 원하는 사용자부터. 되돌아가지 않는다 | 며칠 |
| **7** | 계수를 보고 기본값 전환 판단 | 숫자가 정한다 | — |

**1번을 건너뛰면 나머지 전부가 감이 된다.**

## 10. 왜 이걸 하는가 — 프라이버시가 아니라 원가다

프라이버시는 좋은 문구지만 그것만으로 이 일을 정당화하지 않는다.
사용자는 정확도가 떨어지면 프라이버시를 포기한다.

**진짜 이유는 구조다.**

```
온디바이스 한계 원가 0
  → 무료 등급을 넉넉하게
  → 넉넉한 무료가 유입이 되고
  → 많이 쓰는 사람만 Pro 로 넘어간다
```

[24-GROWTH-STRATEGY §2.2](../product/24-GROWTH-STRATEGY.md) 와 같은 이야기다.
프라이버시는 이 구조를 골랐을 때 **따라오는 결과**이고, 결과가 좋다고 해서
그것이 이유가 되지는 않는다.

그리고 한 가지 더 — **인식한 글자가 기기를 떠나지 않으면,
[24장 §6](../product/24-GROWTH-STRATEGY.md)의 정정 데이터를 다루기가 훨씬 쉬워진다.**
원문이 애초에 나간 적이 없으면, 차이의 모양만 내보내는 설계가 자연스러워진다.
