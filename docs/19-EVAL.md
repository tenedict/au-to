# 분석 품질 평가

> **프롬프트를 고쳐도 좋아졌는지 나빠졌는지 말할 수 있게 하는 것**이 목적이다.
> 첫 측정 2026-08-02

관련 — [`backend/eval/`](../backend/eval/) · [12장 §3](12-IMPLEMENTATION-READINESS.md)

---

## 0. 왜 만들었나

배포하고 실제로 불러 보니 `confidence` 가 이상했다. 그런데 **고칠 수 없었다** —
프롬프트를 바꾼 뒤 좋아졌는지 나빠졌는지 잴 방법이 없었기 때문이다.

한 케이스로 확인하면 그 케이스에만 맞춘 것이 된다. 기준선이 먼저다.

```bash
node backend/eval/run.mjs                                  # 로컬 백엔드
BASE_URL=https://… KEY=… node backend/eval/run.mjs         # 배포된 서버
```

**실제 OpenAI 를 부르므로 요금이 나간다.** 그래서 `verify.sh` 에 넣지 않았다 —
사람이 부를 때만 돈다.

## 1. 무엇을 재나

| | |
| --- | --- |
| 날짜 정확도 | `due_at` 이 기대한 날짜/시각인가 |
| 종일 판정 | `has_explicit_time` 이 맞는가 |
| **모호함을 모호하다고 말하는가** | ← 가장 중요 |
| confidence 분포 | 최소·평균·최대와 폭 |
| 지연 | 중앙값·최대 |

**세 번째가 핵심이다.** 앱은 `ambiguities` 가 비어 있으면 맥에서 **확인 없이
캘린더에 넣는다** (`AutoFilePolicy`). 모호한데 조용하면 사고가 난다.

반대도 본다 — **분명한데 모호하다고 하면** 사용자는 "날짜 분명한데 왜 또 물어봐"가 된다.

### 케이스 15건

| 종류 | 개수 | 예 |
| --- | --- | --- |
| 명확 | 3 | "8월 12일 오후 3시 정기검진 예약이 확정되었습니다" |
| 상대 날짜 | 4 | "다음 주 화요일까지", "이번 달 말일까지" |
| 모호 | 3 | "3월 5일 2시에 봐요" (연도·오전오후 없음) |
| 날짜 없음 | 3 | 광고 · 장보기 목록 · 날씨 |
| 지난 날짜 | 1 | "7월 20일 오후 2시 상담 예약" |
| OCR 잡음 | 1 | 예약 앱 스크린샷의 구분선·버튼 텍스트 |

실제 스크린샷은 개인정보가 있어 넣지 않는다. **익명화한 원문만** 남긴다.

## 2. 첫 측정 (2026-08-02)

### 15건은 기준선으로 쓰기에 작다

같은 프롬프트로 세 번 돌렸다.

```
87%  ·  87%  ·  73%
```

**실행 간 편차가 개선폭보다 크다.** 정확도 하나로는 아무 판단도 할 수 없다는 뜻이다.

`confidence` 최소값도 흔들렸다 — 0.60 · 0.80 · 0.60.

> 그래서 `S-2.3` 의 목표가 50건이다. 지금 15건은 **방향을 보는 데까지**만 쓴다.

### 그래도 일관된 것은 믿을 수 있다

| | 3회 결과 | 판단 |
| --- | --- | --- |
| `nodate-03` "오늘 날씨: 맑음, 최고 31도" | 3/3 실패 | **진짜 결함** — "오늘"을 마감으로 잡는다 |
| `past-01` "7월 20일 오후 2시 상담 예약" | 3/3 실패 | **진짜 결함** — 지난 날짜인데 모호하다고 하지 않는다 |
| 명확 3건 | 3/3 통과 · conf 1.00 | 안정적 |
| 모호 3건 | 3/3 통과 | 안정적 |

## 3. 고친 것 — 모호점 노이즈

### 증상

날짜가 분명한데 "시각이 없다"를 모호점으로 넣었다.

```
"다음 주 화요일까지 서류 제출해 주세요"
  → due_at 2026-08-11 (정확)
  → ambiguities ["'다음 주 화요일'의 정확한 날짜는 '2026-08-11'로 추정됨, 시간은 명시되지 않음"]
```

그러면 맥에서 **확인 화면이 뜬다.** 사용자는 "날짜 분명한데 왜 물어봐"가 된다.
게다가 이 문구는 사용자가 **고칠 수 있는 것이 아니다** — 추론 과정을 설명한 것뿐이다.

### 프롬프트에 더한 것

```
- ambiguities는 사용자가 직접 고쳐야 하는 것만 적는다.
- 날짜가 분명하면 시각이 없어도 ambiguities에 넣지 않는다. 종일 할 일이다.
- 어떻게 추론했는지 설명하지 않는다. 근거는 evidence에만 넣는다.
```

### 결과

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| `relative-01` "다음 주 화요일까지" | ✕ | **✓ (3/3)** |
| `relative-03` "이번 달 말일까지" | ✕ | **✓ (3/3)** |
| 전체 정확도 | 87% | 87% · 87% · 73% |

**목표한 항목은 확실히 고쳐졌다.** 전체 정확도는 편차 안이라 말할 수 없다.

> 이게 기준선 없이 프롬프트를 만지면 안 되는 이유다. "전체가 좋아졌다"고 말할 뻔했다.

## 4. `confidence` 에 대한 정정

12장에 **"confidence 가 0.9~1.0 으로만 나와 눈금 역할을 못 한다"** 고 적었다.
그건 **4건을 보고 내린 결론**이었다.

15건을 보니 다르다.

| 입력 | confidence |
| --- | --- |
| "다음 주에 한번 보자" (요일 없음) | **0.60~0.70** |
| "금요일 미팅 확정입니다" | 0.80 |
| 명확한 예약 문자 | 1.00 |

**눈금 역할을 하고는 있다.** 다만 위쪽에 몰려 있고 폭이 좁다(0.60~1.00, 평균 0.93).
임계값 `0.80` 이 걸러 내는 것은 15건 중 1~2건이다.

`AutoFilePolicy` 가 `ambiguities` 를 `confidence` 보다 먼저 보는 판단은 여전히 맞다 —
`ambiguities` 쪽이 더 많이 걸러 낸다. 다만 "confidence 는 쓸모없다" 는 과했다.

## 6. 우리 한도에 우리가 걸렸다

첫 실행에서 15건 중 5건이 429 로 죽었다. 분당 10회 한도에 평가 스크립트가 걸린 것이다.

**한도를 올리지 않고 스크립트가 스스로 속도를 맞추게 했다** (`PACE_MS`, 기본 6.5초).
평가하자고 운영 설정을 만지면 평가가 끝난 뒤 되돌리는 것을 잊는다.

로컬 백엔드로 돌릴 때는 `PACE_MS=300` 으로 줄인다 — 30초면 한 바퀴 돈다.
반복이 빨라야 프롬프트를 고쳐 볼 수 있다.
