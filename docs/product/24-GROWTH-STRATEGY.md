# 성장 전략 — 수익화 · B2B · 일정 플랫폼

> 이 문서는 **계획이 아니라 판단의 근거**다. 숫자 대부분은 아직 측정하지 않은
> 가정이고, 가정마다 어떻게 확인할지를 함께 적었다.
> 2026-08-03 작성 · 실사용자 0명 시점의 문서다. 첫 100명이 생기면 전면 재작성한다.

## 0. 세 줄 요약

1. **우리가 가진 것은 캘린더가 아니라 그 앞의 30초다.** 이미지로 도착한 정보가
   약속이 되는 구간 — 여기를 소유한 앱이 아직 없다.
2. **수익화의 축은 "얼마나 많이 담느냐"다.** 이미 `IntakeRate` 가 그 단위를 세고
   있고, 온디바이스 모델이 무료 등급의 원가를 0 으로 만든다.
3. **B2B 의 값은 앱이 아니라 "안 나타난 사람 수"다.** 병원·학원·공공이 실제로
   돈을 내는 지표는 노쇼율이지 편의성이 아니다.

## 1. 우리가 실제로 소유한 것

캘린더 앱을 만들면 안 된다. Apple 과 Google 이 이미 갖고 있고, 무료이고, 기본 앱이다.
할 일 앱도 안 된다. Things · Todoist · 미리 알림이 10년째 그 자리에 있다.

**둘 사이가 비어 있다.**

```
정보가 도착한다        →        [ 비어 있음 ]        →        약속이 된다
예약 문자 · 가정통신문                                        캘린더 · 미리 알림
공지 사진 · 접수증
```

이 구간에서 사람이 지금 하는 일은 이렇다.

```
스크린샷 → 나중에 봐야지 → 잊음 → 사진첩에 1,400장
```

**Whenly 는 이 구간만 한다.** 캘린더와 싸우지 않고 캘린더에 **넣어 준다**.
경쟁 상대는 다른 앱이 아니라 **사진첩과 기억력**이다.

### 이 자리가 방어 가능한 이유

| 자산 | 왜 따라 하기 어려운가 |
| --- | --- |
| **담는 자리의 수** | 공유 시트 · 물방울 · Dock · 잠금화면 위젯 · 카메라. 하나씩은 쉽지만 전부 갖추는 데 시간이 든다 |
| **한국어 일정 문장** | "다음 주 화요일", "이번 달 말일", "8/5(수) 14:00". 범용 모델은 여기서 틀린다 |
| **평가셋** | [19-EVAL](../engineering/19-EVAL.md). 프롬프트를 감이 아니라 근거로 고칠 수 있다 |
| **정정 데이터** | 사용자가 **무엇을 고쳤는가**. 이건 우리만 갖는다 (§6) |

### 이 자리가 위험한 이유

**Apple 이 같은 자리를 보고 있다.** Visual Intelligence 는 이미 사진 속 날짜를
캘린더에 넣자고 제안한다. 그러니 "이미지에서 날짜 뽑기" 자체는 해자가 아니다.

우리가 남는 근거는 하나뿐이다 — **끝까지 간다는 것.**
Apple 은 제안하고 끝난다. 우리는 등록하고, 알리고, 고치게 하고, 지난 것을 세고,
반복을 알아본다. 기능 하나가 아니라 **일정 하나의 생애 전체**가 제품이다.

## 2. 수익화

### 왜 구독인가

이 제품의 원가는 **담는 횟수에 비례한다.** 분석 한 번은 OCR + LLM 호출 한 번이다.
한 번 팔고 끝나는 가격표를 붙이면, 많이 쓰는 사용자일수록 손해가 커진다 —
**가장 좋아하는 사용자를 벌하는 구조**가 된다.

### 등급

| | 무료 | Pro | Family |
| --- | --- | --- | --- |
| 담기 | **월 30건** | 무제한 (남용 방지 상한만) | 무제한 · 5인 |
| 분석 | 온디바이스 우선 | 클라우드 (더 정확) | 클라우드 |
| 한 장에서 여러 일정 | 1건만 | 전부 | 전부 |
| 캘린더 연동 | 넣기 | 넣기 + 고치기 동기화 | 좌동 |
| 위젯 | 잠금화면만 | 전부 | 전부 |
| 지난 캡처 다시 보기 | 7일 | 무제한 | 무제한 |

**무료를 쓸모없게 만들지 않는다.** 월 30건은 대부분의 사람에게 충분하다.
돈을 내는 사람은 "많이 쓰는 사람" 이지 "기능이 잠긴 사람" 이 아니어야 한다.
잠긴 기능으로 짜증을 만들면 지우고 끝이다.

> **가격은 여기 적지 않는다.** 실사용자 0명인 지금 정하는 가격은 근거가 없다.
> 정하는 방법만 적는다 → §2.3.

### 2.1 원가 구조 — 계산식만 적는다

```
캡처 1건 원가 = OCR(0, 온디바이스)
              + LLM 호출 1회
              + 백엔드 실행 시간
```

| 변수 | 지금 값 | 어디서 확인 |
| --- | --- | --- |
| 입력 토큰 | OCR 텍스트 20~300자 ≈ 30~250 토큰 | `server/eval/cases.json` |
| 출력 토큰 | 구조화 JSON ≈ 100~300 토큰 | 같은 곳 |
| 모델 단가 | **측정 안 함** | 구현 직전 공식 가격표에서 채운다 |
| 월 캡처 수 | **측정 안 함** | 첫 100명에서 나온다 |

**이 표에 실제 숫자를 채우기 전에는 가격을 정하지 않는다.**
단가를 모르고 정한 가격은 도박이지 전략이 아니다.

### 2.2 온디바이스가 곧 수익 구조다

무료 등급을 **온디바이스 우선**으로 두면 무료 사용자의 한계 원가가 0 에 수렴한다.
그러면 무료 한도를 넉넉히 줄 수 있고, 넉넉한 무료가 곧 유입이 된다.

```
무료 사용자 원가 0  →  무료 한도를 크게  →  유입이 늘고
                                        →  많이 쓰는 사람만 Pro 로 넘어간다
```

이건 마케팅 문구가 아니라 **구조**다. 자세한 것은
[23-ONDEVICE-LLM-STRATEGY](../platform/23-ONDEVICE-LLM-STRATEGY.md).

### 2.3 가격을 정하는 방법

| 단계 | 무엇 |
| --- | --- |
| 1 | 첫 100명에게 **전부 무료.** 대신 월 캡처 수 분포를 잰다 |
| 2 | 상위 20% 가 쓰는 양을 본다. 무료 한도를 **그 아래**로 잡는다 |
| 3 | 실제 단가 × 상위 20% 사용량 = Pro 의 원가 하한 |
| 4 | 국내 구독 앱의 심리적 상한(커피 한 잔)과 비교해 결정 |

한도를 상위 20% 아래로 잡는 이유 — 한도에 **닿아 본 사람만** 결제를 생각한다.
아무도 닿지 않는 한도는 없는 것과 같다.

## 3. B2B — 값은 "안 나타난 사람 수"다

편의성으로는 기업이 돈을 내지 않는다. **손실이 줄어야** 낸다.

### 3.1 노쇼가 실제 돈인 곳

| 대상 | 손실 | Whenly 가 줄이는 방식 |
| --- | --- | --- |
| **병원 · 검진센터** | 예약 부도 1건 = 그 슬롯의 매출 전부 | 예약 문자 → 자동 등록 → 마감 알림 2회 |
| **학원 · 교습소** | 상담 · 레벨테스트 결석 | 안내문 사진 → 학부모 일정 |
| **공공 검진 · 접수** | 재안내 비용, 기한 경과 민원 | 통지서 → 마감 알림 |
| **정비 · 시공 방문** | 부재로 인한 재방문 | 방문 예정 문자 → 등록 |

**측정 가능한 값이 있다.** "예약 부도율 12% → 9%" 는 계약서에 쓸 수 있는 문장이고,
"편해집니다" 는 아니다.

### 3.2 파는 방식 셋

**A. 담기 버튼 (B2B2C · 가장 가볍다)**

기관이 보내는 문자·메일 아래에 링크 하나를 붙인다.

```
[강남치과] 8월 12일 오후 3시 검진 예약이 확정되었습니다.
▸ 내 일정에 담기  https://wh.ly/a/xxxxx
```

누르면 Whenly 가 열리고 이미 채워진 확인 화면이 뜬다. OCR 도 LLM 도 필요 없다 —
**기관이 이미 구조화된 데이터를 갖고 있기 때문**이다. 원가가 0 에 가깝고 정확도는 100%.

> 이 길은 우리 제품의 핵심 기술을 **쓰지 않는다.** 그게 강점이다.
> 기술이 아니라 **약속이 등록되는 자리**를 파는 것이고, 그 자리가 우리 것이다.

**B. 파싱 API (B2B)**

이미 `server/` 가 있다. 문자·이미지를 넣으면 일정 JSON 이 나온다.
CRM · 예약 시스템 · 메신저 봇이 부른다. 과금은 호출당.

**C. 사내 배포 (Enterprise)**

공지 → 직원 일정. 관리자 콘솔 · SSO · 데이터 잔류 정책이 필요하다.
**지금 구조로는 못 판다** → §5.

### 3.3 순서

```
1) 담기 버튼   기존 앱 그대로. 링크 스킴 하나 + 랜딩 하나
2) 파싱 API    이미 있는 백엔드에 키 발급과 사용량 미터만 얹으면 된다
3) 사내 배포   계정 · 조직 · 감사 로그가 먼저다. 지금 하면 안 된다
```

1번은 **몇 주**, 3번은 **몇 분기**다. 순서를 뒤집으면 안 된다.

## 4. 플랫폼으로 가는 계단

한 번에 뛰지 않는다. 각 층은 **아래 층이 쌓아 준 데이터가 있어야** 성립한다.

```
5층  일정 그래프 API   다른 앱이 "이 사람 언제 비나" 를 묻는다
4층  대리              예약 확인 회신 · 리스케줄 제안
3층  예측              반복 알아보기 · 준비 시간 역산
2층  지키기            충돌 감지 · 놓친 것 되살리기
1층  담기              ← 지금 여기
```

### 1층 → 2층 · 지키기 (다음 분기)

담기만 하면 **캘린더에 넣어 주는 도구**로 끝난다. 지켜 줘야 제품이 된다.

| 기능 | 왜 지금 가능한가 |
| --- | --- |
| **충돌 감지** | 같은 시각에 둘이면 등록할 때 말해 준다. `DueGrouping` 이 이미 시각을 안다 |
| **중복 감지** | 같은 예약을 두 번 담는 일이 실제로 잦다. 이미 다음 할 일로 잡혀 있다 |
| **놓친 것 되살리기** | 지난 마감이 쌓이면 "다시 잡을까요?" — 지금은 그냥 빨갛게 남는다 |

### 2층 → 3층 · 예측

```
같은 병원 · 3개월 간격 · 3회      →  "다음 검진 시기예요"
9시 예약 · 그 병원까지 40분        →  "8시에 나서야 해요"
매월 25일 관리비                   →  자동 반복 제안
```

**이건 큰 모델이 필요 없다.** 개인의 반복 패턴은 자기 원장 안에 있고,
계산이지 추론이 아니다 — `core/swift/Models/` 에 순수 함수로 들어간다.

### 3층 → 4층 · 대리 (조심할 층)

예약 확인 문자에 자동으로 답하거나 변경을 요청하는 층이다.
**사람 대신 약속을 만드는 순간 제품의 성격이 바뀐다.**

CLAUDE 규칙 1 의 정신 — 사람이 최종 판단을 한다 — 이 여기서 시험받는다.
이 층은 **되돌릴 수 있는 것만** 자동으로 한다. 취소·확정처럼 상대가 있는 행동은
언제나 사람이 누른다.

### 4층 → 5층 · 일정 그래프 API

"이 사람이 다음 주 목요일 오후에 비어 있는가" 를 다른 앱이 묻는다.
캘린더 API 와 다른 점은 **의도와 유연성을 안다**는 것이다 —
"관리비 납부" 는 옮길 수 있고 "검진 예약" 은 옮길 수 없다.

이 구분은 우리가 담을 때 이미 만들어진다.

## 5. 지금 구조가 막고 있는 것

정직하게 적는다. **아래 넷을 풀지 않으면 §3-C 와 §4 의 4·5층은 불가능하다.**

| 벽 | 지금 | 필요한 것 |
| --- | --- | --- |
| **계정이 없다** | 원장이 기기 안의 `tasks.json` 하나 | 기기 간 동기화. CloudKit 이 가장 싸다 |
| **조직 개념이 없다** | 사용자 = 기기 | 조직 · 역할 · 감사 로그 |
| **사용량 미터가 없다** | `IntakeRate` 는 **속도**만 잰다. 총량은 안 센다 | 월 단위 카운터 (무료 한도의 전제) |
| **정정 데이터를 안 남긴다** | 사용자가 고쳐도 원본과의 차이가 사라진다 | §6 |

계정을 만들면 **프라이버시라는 자산을 일부 잃는다.** 그래서 순서가 중요하다 —
CloudKit(사용자의 iCloud, 우리는 못 봄)이 먼저고, 우리 서버 계정은 B2B 가
실제 매출을 낼 때만이다.

## 6. 가장 값진 데이터는 정정이다

지금은 사용자가 초안을 고쳐도 **무엇을 고쳤는지가 사라진다.**
`TaskEdit.apply(to:)` 가 새 값을 얹고 끝이다.

원본과 정정본의 차이는 이 제품에서 가장 값진 신호다.

```
모델: "다음 주 화요일" → 8/11
사용자가 고침:          → 8/18
```

이 한 줄이 말하는 것 — **"다음 주" 의 기준 주가 어긋난다.**
평가셋 15건으로는 절대 못 잡는 종류의 오류이고, 실사용자 100명이면 매일 나온다.

### 지켜야 할 것

| | |
| --- | --- |
| **기기 밖으로 내보내지 않는다** | 원문에는 이름·병원·금액이 있다 |
| 내보낼 수 있는 것 | "상대 날짜 표현이 N일 어긋남" 같은 **차이의 모양**뿐 |
| 켜는 방식 | 기본 꺼짐. 설정에서 사용자가 켠다 |

이건 프라이버시 문구가 아니라 §1 의 해자를 지키는 일이다 —
**우리가 프라이버시를 이유로 남는 앱이면, 그 이유를 우리가 깨면 안 된다.**

## 7. 무엇을 재나

허영 지표를 쓰지 않는다. 다운로드 수는 아무것도 말하지 않는다.

| 지표 | 무엇을 말하나 | 왜 이것인가 |
| --- | --- | --- |
| **담기 → 등록 전환율** | 분석이 쓸 만한가 | 낮으면 모델이 문제고, 높은데 안 쓰면 유입이 문제다 |
| **정정률** | 분석 품질의 **진짜** 값 | `confidence` 는 눈금 역할을 못 한다 ([19-EVAL §4](../engineering/19-EVAL.md)) |
| **재담기율** | 사람이 이 앱을 신뢰하나 | 한 번 쓰고 마는 것과 습관의 차이 |
| **D7 담기 유지** | 습관이 되었나 | 열어 본 것이 아니라 **담은 것**을 센다 |
| **지난 마감 비율** | 지켜 주고 있나 | 담기만 하고 놓치면 사진첩과 같다 |

마지막 지표가 2층(§4)의 존재 이유다. **이 숫자가 내려가지 않으면 제품이 실패한 것**이고,
담기 횟수가 아무리 늘어도 소용없다.
