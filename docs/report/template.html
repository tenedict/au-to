01

기획 — 무엇을 왜 만드는가

메신저, 예약 화면, 공지, SNS에서 “나중에 해야 할 것”을 스크린샷으로 남기지만 사진첩에 묻힌다. 사용자는 다시 읽고, 날짜를 찾고, 할 일과 캘린더에 중복 입력한다 — 대개는 그 세 단계를 하지 않는다.

“스크린샷을 한 번 공유하면 해야 할 일이 정리되고, 마감이 다가오면 알려 준다.”

핵심 사용자

예약·공지·업무 요청·행사 정보를 스크린샷으로 자주 저장하는 iPhone 사용자. 전형적인 하루 — 병원 예약 확정 문자, 관리비 고지, 행사 안내, 회의 시간 변경. 전부 화면에 있고, 전부 나중에 해야 하고, 전부 사진첩에 쌓인다.

차별점

실행 가능한 할 일로 바꾼다범용 노트 앱이 아니다. 제목과 마감이 있는 한 줄이 결과다
마감이 급한 순으로 보여준다지갑처럼 쌓인 카드에서 지난 마감이 맨 위에 있다
놓치기 전에 알려 준다로컬 알림 3종. 서버가 사용자의 할 일을 알 필요가 없다
소유권을 분리한다앱 할 일이 원장, Apple 캘린더는 선택적 출력
로컬 우선, 확인 우선OCR 은 기기에서. AI 결과는 사람이 확인한 뒤에만 저장된다

하지 않기로 한 것

하지 않는다왜
AI 가 확인 없이 자동 저장일정 오인식 하나가 앱 전체의 신뢰를 없앤다
캘린더 양방향 동기화“어느 쪽이 진짜인가”를 사용자도 코드도 답할 수 없게 된다
원본 이미지를 서버로 전송스크린샷에는 대화·주소·예약 정보가 그대로 있다
서버 푸시 알림서버가 사용자의 할 일과 마감을 알아야 한다
앱 안의 완전한 캘린더 앱Apple 캘린더가 이미 있다. 앱을 나가지 않을 정도만

02

PRD — 원칙 · 결정 · 범위

여섯 개의 원칙이 이 제품의 모든 판단을 가른다. 판단이 갈릴 때 코드가 아니라 이 목록을 먼저 본다.

제품 원칙

1캡처를 잃지 않는 것이 자동화 속도보다 중요하다. 분석·캘린더·알림이 전부 실패해도 담아 둔 스크린샷은 남는다.
2틀린 자동 저장보다 한 번의 명확한 확인이 낫다. 확인 화면을 지나지 않는 저장 경로는 없다.
3앱 할 일이 원장이고 나머지는 시점이다. 캘린더도, 캘린더 탭도, 알림도 원장이 아니다.
4로컬에서 충분한 처리는 로컬에서 한다. 나가는 것은 OCR 텍스트뿐이다.
5AI 공급자는 교체 가능해야 한다. 고르는 지점이 한 곳이어야 옮길 수 있다.
6실패는 조용하면 안 된다. 자동 대체도, 삼킨 오류도, 없다고 통과시키는 검사도 만들지 않는다.

여덟 영역으로 나뉜 기능 요구사항(FR)과 불변 조건. 각 요구사항은 코드의 한 지점과 테스트 한 건에 대응한다.

영역접두사개수핵심
캡처 수집FR-CAP6담기가 분석보다 먼저. 죽어도 캡처가 남는다
텍스트·문맥 분석FR-AI8OCR 은 온디바이스, 문맥은 백엔드. 한 장에서 여러 일정
확인FR-REV9저장·나중에·버리기. 확인 없는 저장 경로 없음
할 일 목록FR-TASK10마감 묶음 6개 · 급한 순 · 완료·삭제
마감 알림FR-NOTI153종 · 식별자 충돌 금지 · 지난 시각은 걸지 않는다

캘린더 뷰FR-MONTH—읽기 전용. 같은 원장의 다른 시점
저장과 복구FR-STORE—원자적 쓰기 · 손상 격리 · 구버전 호환
불변 조건

요구사항보다 강한 것이 불변 조건 14건이다. “확인 화면을 지나지 않는 저장 경로가 존재하지 않는다”, “캡처를 지우는 코드 지점이 하나뿐이다” 같은 문장들이고, 대부분 scripts/check-project-rules.sh 가 매 커밋 기계적으로 확인한다.

마감 묶음 — 순서가 곧 의미다

지난 마감 → 오늘 → 앞으로 7일 → 그 뒤 → 날짜 없음 → 완료

위에 있을수록 급하다. 순서의 유일한 근거는 DueBucket 의 선언 순서다. 화면은 정렬을 다시 하지 않는다 — 정렬 지점이 둘로 갈라지면 “왜 이게 위에 있지”를 아무도 설명하지 못하게 된다.

시간이 명시된 할 일은 그 시각이 지나면 같은 날이라도 지난 마감이다. 날짜만 비교하면 “오후 2시 예약”이 오후 6시에도 오늘 할 일로 남는다.

물방울 아이콘 — 기술 검토

요청은 둘이다. ① 메뉴바 아이콘을 유리에 맺힌 물방울로 — 완벽한 원이 아닌, 자연스럽게 맺힌 모양. ② 떠 있는 물방울을 스테인리스 고리가 아니라 밑 화면이 비치고 빛이 굴절되는 진짜 물방울로.
답을 추측하지 않고 실험 네 개를 돌렸다.

A-1 · 메뉴바 아이콘 — 가능하다. 단, 모양뿐이다.

메뉴바 아이콘은 템플릿 이미지다. 시스템이 알파 채널만 보고 색을 스스로 칠한다 — 밝은 메뉴바에서는 검정, 어두운 메뉴바에서는 흰색, 눌리면 반전. 그래서 여기서 정할 수 있는 것은 실루엣 하나뿐이고, 굴절도 색도 그라디언트도 들어가지 않는다.

“완벽한 원이 아닌, 맺힌 물방울”은 그 제약 안에서 표현할 수 있다. 실제 물방울은 표면장력과 중력이 함께 만든 모양이라 아래가 조금 넓고 평평하고, 위가 더 둥글고, 좌우가 완전히 대칭이 아니다. 그 미세한 어긋남이 “그려진 원”과 “맺힌 물”을 가른다.

후보성격18pt 에서
A · 윤곽만가장 조용하다. 물방울보다 “원”으로 읽힐 위험선명하나 밋밋
B · 윤곽 + 광점광점 하나가 “젖은 것”을 만든다권장 — 작아져도 광점이 살아남는다
C · 채움 + 광점 파냄가장 눈에 띈다. 메뉴바에서 다소 무겁다또렷하나 존재감이 과하다
D · 유리에 닿음“유리에 맺혔다”는 서사가 가장 강하다선이 둘이라 작을수록 뭉갠다
판정
가능 — 오늘 바로 바꿀 수 있다

현재 MenuBarExtra("CaptureTask", systemImage: "drop.fill") 로 SF Symbol 을 쓰고 있다. 커스텀 템플릿 이미지로 교체하는 작업이며 코드 변경은 작다. 권장은 B. 색을 넣고 싶다면 isTemplate = false 로 가능하지만, 메뉴바에서 색을 쓰는 앱은 시스템과 어울리지 않아 보이므로 권하지 않는다.

A-2 · 떠 있는 물방울의 “진짜 굴절” — 공개 API 로는 불가능하다

먼저 결론을 말하고 근거를 붙인다. macOS 에는 “내 창 뒤에 있는 다른 앱의 화면을 굴절시키는” 공개 API 가 없다. 흐림(blur)은 있고, 굴절은 없다.

실험 1 — CALayer.backgroundFilters + CIBumpDistortion

이 API 는 이름 그대로 “레이어 뒤에 있는 것”에 Core Image 필터를 건다. 창이 투명하면 그 뒤는 다른 창이니, 된다면 진짜 굴절이다. 격자 무늬 창을 깔고 그 위에 필터를 건 투명 패널을 띄웠다.

실험 2 — NSVisualEffectView 와 macOS 26 Liquid Glass

Apple 이 제공하는 “유리” 두 가지를 같은 배경 위에 놓고 비교했다. 굴절은 직선이 휘는 것으로만 증명된다 — 흐림·틴트·가장자리 하이라이트는 굴절이 아니다.

즉 Liquid Glass 는 서리 낀 유리이지 렌즈가 아니다. 사용자가 요청한 “밑의 화면이 자연스럽게 보이고 빛의 굴절이 보이는” 것과는 다르다.

A-3 · 남은 유일한 길 — 뒤를 우리가 캡처해서 우리가 왜곡한다

시스템이 굴절시켜 주지 않는다면, 뒤 화면을 직접 얻어서 우리가 렌즈를 계산해 그리면 된다. 순서는 이렇다.

  1. ScreenCaptureKit 으로 물방울이 덮고 있는 화면 영역을 실시간 캡처한다. 이때 SCContentFilter(display:excludingWindows:) 로 물방울 창 자신을 반드시 제외해야 한다 — 아니면 물방울이 물방울을 비추는 무한 되먹임이 생긴다.
  2. 그 이미지에 Core Image 로 렌즈 왜곡을 건다 (CIBumpDistortion 또는 커스텀 Metal 셰이더).
  3. 맺힌 물방울 모양으로 마스크하고, 어두운 가장자리·림라이트·하이라이트를 얹는다.
  4. 매 프레임 다시 그린다.

2~4단계의 광학이 실제로 통하는지 먼저 확인했다. 캡처 대신 이미 있는 화면 이미지를 배경으로 넣고 같은 파이프라인을 돌렸다.

대가
비용내용
화면 기록 권한시스템 설정에서 사용자가 직접 켜야 하고, 최근 macOS 는 주기적으로 재확인을 요구한다. 68pt 장식 하나를 위해 “이 앱이 화면 전체를 봅니다” 를 승인받아야 한다
제품 원칙과 충돌이 앱은 “원본 이미지는 기기를 떠나지 않는다”를 팔고 있다. 그 앱이 상시 화면 캡처 권한을 요구하는 것은 설명하기 어려운 모순이다. 기술적으로 안전해도 사용자가 그렇게 읽지 않는다
지속 비용물방울은 항상 떠 있다. 상시 캡처 + 매 프레임 GPU 합성은 유휴 상태의 배터리·발열에 그대로 들어간다
되먹임자기 창 제외를 놓치면 즉시 무한 반사. 다중 디스플레이·해상도 변경·Space 이동마다 필터를 다시 만들어야 한다
샌드박스현재 macOS 타깃은 샌드박스에 files.user-selected.read-only 만 있다. 화면 캡처 권한은 별개의 TCC 승인이다
판정
기술적으로 가능하다 — 그러나 권하지 않는다

“진짜 굴절”은 구현할 수 있고, 위 실험 3·4 가 그 결과물을 보여준다. 다만 얻는 것은 장식이고 치르는 것은 화면 전체 접근 권한과 이 제품의 프라이버시 서사다. 교환비가 맞지 않는다.

A-4 · 권고 — 권한 없이 “물방울”에 도달하는 세 단계

굴절 자체보다 물방울로 읽히게 하는 것이 목표라면, 권한 없이 갈 수 있는 곳이 생각보다 멀다. 실험 4 에서 확인한 것은 물방울의 인상을 만드는 것이 굴절이 아니라 모양 · 어두운 가장자리 · 하이라이트였다는 점이다.

단계무엇권한비용
1모양을 물방울로. 스테인리스 고리를 버리고 맺힌 윤곽 + 어두운 가장자리 + 하이라이트 둘. 가운데는 지금처럼 완전 투명이라 뒤가 그대로 보인다없음작음
2유리를 더한다. 가운데를 macOS 26 .glassEffect() 로 아주 옅게 채운다. 굴절은 없지만 “물이 고여 있다”가 생긴다. macOS 26 미만은 1단계로 떨어진다없음작음
3드롭할 때만 진짜 굴절. 끌어다 놓기가 시작될 때 한 번만 뒤를 캡처해 굴절시키고, 놓으면 되돌린다. 상시 캡처가 아니라 사용자 행동에 붙은 일회 캡처라 설명이 된다화면 기록중간

1단계만으로도 지금보다 훨씬 물방울에 가깝다. 지금 화면에 있는 것은 금속 고리이고, 사용자가 “스테인리스 원이 아니라”고 말한 대상이 정확히 그것이다. 2단계까지는 권한도 지속 비용도 없다.

실험 재현

이 부록의 네 실험은 모두 이 저장소 밖의 임시 스크립트로 돌렸고, 각각 swiftc 로 컴파일되는 단일 파일이다. 결과 이미지는 전부 실제 화면 캡처이며 합성하지 않았다. 코드를 저장소에 남기길 원하면 docs/platform/ 아래 스파이크로 넣을 수 있다.
